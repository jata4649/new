# ポイント台帳の説明書

ポイントの記録方式・有効期限・消費順序・整合性検証。

---

## 1. 三層構造

```
┌──────────────────────────────────────────────────────┐
│ point_ledger_entries   ★唯一の真実（追記専用）        │
│   いつ・誰が・何の理由で・いくら動いたか               │
│   UPDATE / DELETE は DB トリガで拒否                  │
└──────────────────┬───────────────────────────────────┘
                   │ 明細
┌──────────────────▼───────────────────────────────────┐
│ point_lot_consumptions  どのロットから何ポイント引いたか│
│   これが無いと REFUND / REVERSAL で元のロットへ戻せない │
└──────────────────┬───────────────────────────────────┘
┌──────────────────▼───────────────────────────────────┐
│ point_lots              有効期限つき残高の実体         │
└──────────────────┬───────────────────────────────────┘
┌──────────────────▼───────────────────────────────────┐
│ point_accounts          高速参照用の集計キャッシュ      │
│   壊れても台帳から再構築できる                         │
└──────────────────────────────────────────────────────┘
```

**残高を単純に上書きしない。** 残高の変更は必ず台帳への記帳を伴う。
`point_accounts` は参照を速くするためのキャッシュに過ぎない。

---

## 2. ポイントの種類と取引種別

| 種類   | 意味                                         | 有効期限                             |
| ------ | -------------------------------------------- | ------------------------------------ |
| `PAID` | 対価を伴って発行されたポイント               | **180 日（6 か月未満）でハード上限** |
| `FREE` | 無償ポイント（ボーナス・商品のポイント交換） | 既定 180 日（変更可）                |

| 取引種別         | 符号 | 説明                                           |
| ---------------- | ---- | ---------------------------------------------- |
| `PURCHASE`       | +    | 決済成功による有償ポイント付与                 |
| `DRAW`           | −    | 抽選によるポイント消費                         |
| `PRIZE_EXCHANGE` | +    | 当選商品をポイントへ交換（無償ポイントで発行） |
| `BONUS`          | +    | キャンペーン等による無償付与                   |
| `ADJUSTMENT`     | ±    | 管理者による調整（**理由必須**）               |
| `EXPIRE`         | −    | 有効期限切れ                                   |
| `REFUND`         | −    | 決済の返金に伴う取消し                         |
| `REVERSAL`       | ±    | 誤記帳の打ち消し（**理由必須**）               |

`ADJUSTMENT` / `REVERSAL` の理由必須は DB の CHECK 制約
（`point_ledger_entries_reason_required_check`）でも強制している。

---

## 3. 有償ポイントの有効期限を 180 日に固定する理由

資金決済法上、前払式支払手段は「発行日から 6 か月以内に限り使用できるもの」が
適用除外となる。6 か月を超える有効期限を設定すると、届出・供託等の義務が
生じうる（本 MVP は法務確認が完了するまで現金を受け取らない前提だが、
将来そのまま本番へ移行しても問題が起きないよう、最初から 6 か月未満に固定する）。

二重に守っている。

1. `src/lib/config/env.ts` — `POINT_EXPIRY_DAYS_PAID > 180` なら**起動時に落とす**
2. `src/lib/config/points.ts` — `calculateExpiresAt` が上限で切り詰める

無償ポイントは対価性が無いためこの制約の対象外であり、期限を自由に設定できる。

### 開発時の短縮

`POINT_EXPIRY_MINUTES_OVERRIDE=5` で分単位に短縮できる。
`NODE_ENV=production` では**無視される**（本番で誤って失効させないため）。

---

## 4. 消費順序

既定（`POINT_CONSUMPTION_STRATEGY=free_first`）:

```
1. 無償ポイント（FREE）を expires_at 昇順
2. 有償ポイント（PAID）を expires_at 昇順
```

同一 `expires_at` の場合は `issued_at` 昇順 → `id` 昇順（決定的に定まるようにする）。

| 戦略                 | 動作                                                       |
| -------------------- | ---------------------------------------------------------- |
| `free_first`（既定） | 無償を先に使い切る。ユーザーにとって有利（有償が長く残る） |
| `paid_first`         | 有償を先に使う                                             |
| `expiry_only`        | 種別を問わず期限が近い順                                   |

実装は `src/lib/config/points.ts` の `consumptionRules()`。
ルールを配列で返す構造にしているため、順序の変更が 1 か所で済む。

### 残高の参照

残高を読むときは**常に `expires_at > now()` で絞る**。
これにより、期限切れバッチが未実行でも期限切れポイントは使えない。
バッチはあくまで台帳への記帳と集計値の同期が目的。

## 5. 消費の流れ（抽選 5,000 ポイントの例）

```
前提: FREE 1,200P（期限 3/1）, PAID 3,000P（期限 4/1）, PAID 2,000P（期限 6/1）

1. 消費対象ロットを FOR UPDATE でロック（自分の行だけなので競合は自分の並行リクエストのみ）
2. free_first の順に割り当て
     FREE  1,200P → 全額消費（amount_remaining 0、exhausted_at 設定）
     PAID  3,000P → 全額消費
     PAID  2,000P → 800P 消費（残 1,200P）
3. point_ledger_entries へ 1 件記帳
     tx_type=DRAW, point_type=null（複数種別にまたがるため）, amount=-5000
4. point_lot_consumptions へ 3 件記帳
     (entry, FREEロット, 1200) (entry, PAIDロット1, 3000) (entry, PAIDロット2, 800)
5. point_accounts を条件付き UPDATE
     WHERE free_balance >= 1200 AND paid_balance >= 3800
```

すべて抽選と同一トランザクション内で行う。

---

## 6. 取消し（REFUND / REVERSAL）

`point_lot_consumptions` を辿り、**同じロットへ戻す**（期限は元のまま）。
これが消費明細テーブルを持つ最大の理由。

既に使い切られている等で戻せない場合は、残高をマイナスにせず
`audit_logs` へ記録し、管理者へ通知する（ダッシュボードの「直近のエラー」に表示）。

---

## 7. 管理者によるポイント調整

要件「直接残高を書き換えない」への対応。

1. 理由の入力を必須にする（UI・API・DB CHECK の三重）
2. `point_ledger_entries` へ `ADJUSTMENT` として記帳する
3. 付与なら新しい `point_lots` を作り、減算なら既存ロットから引く
4. `audit_logs` へ `actor_id` とともに記録する

`point_accounts` を直接 UPDATE する経路はコード上に存在しない
（`PointService` 以外から書き込めないようモジュール境界で制限する）。

---

## 8. 整合性の検証

`pnpm points:reconcile` で以下を検証する（読み取り専用・自動修復しない）。

| 検査     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| INV-1    | Σ(台帳の amount) == 口座残高                                 |
| INV-2    | Σ(ロットの amount_remaining) == 口座残高                     |
| INV-3    | 0 ≤ amount_remaining ≤ amount_issued                         |
| 消費明細 | Σ(consumptions.amount) == (amount_issued − amount_remaining) |

不整合が 1 件でもあれば終了コード 1 を返すため、CI や定期実行で失敗を検知できる。

**自動修復しない理由**：原因を確認せずに残高を書き換えるのは、
金銭事故を隠す行為になりうるため。台帳が真実であり、直すべきはキャッシュ側。

---

## 9. 物理削除しない

以下は `deletedAt` すら持たない完全な追記専用テーブル。

- `point_ledger_entries`
- `point_lot_consumptions`
- `draw_transactions`
- `draw_results`
- `audit_logs`

DB トリガ（`reject_mutation_on_append_only_table`）が UPDATE / DELETE を拒否し、
エラーメッセージに `APPEND_ONLY_VIOLATION` を含める。
加えて、本番では実行時ロール `oripa_app` から UPDATE / DELETE 権限を剥奪する。

> トリガは TRUNCATE を対象にしていないため、テストのクリーンアップや
> `prisma migrate reset` は影響を受けない。
> テストのデータ削除には DELETE ではなく TRUNCATE を使うこと
> （`src/tests/helpers/setup-db.ts`）。
