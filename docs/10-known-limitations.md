# 既知の制約一覧

MVP（クローズドテスト版）時点で意図的に受け入れている制約と、
本番化の前に解消すべき事項。

---

## 1. 設計上の制約（意図的なトレードオフ）

### 1-1. 事前シャッフル順は DB 閲覧者に見えてしまう

抽選は公開前に `draw_order`（順列）を確定させる方式を採っている。
そのため、**DB へ直接アクセスできる人物は「次に何が出るか」を知りうる**。

| 現状の緩和策                                               | 状態                                 |
| ---------------------------------------------------------- | ------------------------------------ |
| `draw_order` を API・管理画面へ露出させない                | 実装方針として確定（Phase 4 で実装） |
| コミットハッシュ（`slot_order_commit`）を公開時に記録      | スキーマに用意済み                   |
| 販売終了後に `serverSeed` を公開して第三者検証を可能にする | 運用手順（Phase 4 で実装）           |
| 本番での DBA ロール分離・踏み台経由アクセスの監査          | **未対応（本番化前に必須）**         |

代替案（抽選時に `ORDER BY random()` で選ぶ）は漏洩リスクが無い代わりに、
毎回テーブル全走査が必要で同時実行性能が落ちる。
MVP では性能と分布の厳密さを優先した。判断を変える場合は
`docs/06-draw-algorithm.md` の比較表を参照のこと。

### 1-2. `remaining_slots` の更新で人気オリパのリクエストが直列化する

同一キャンペーンの抽選は、トランザクション末尾の
`UPDATE oripa_campaigns SET remaining_slots = ...` で行ロックを取り合う。
数十 req/s 程度であれば問題にならないが、それ以上ではボトルネックになる。

解消案（必要になってから実装）:

- シャード化カウンタ（`campaign_id, shard_no` に分割して集計）
- `remaining_slots` を持たず、部分インデックス上の件数から求める

### 1-3. セッション確認で毎リクエスト DB を 1 回引く

Auth.js の Credentials プロバイダが JWT 戦略に限られるため、
停止・失効の即時反映のために毎回 DB を引く構成にしている
（[01-architecture.md](./01-architecture.md) §8）。
残高・在庫の確認で結局 DB を引くため追加コストは実質 1 クエリだが、
参照専用ページでも 1 クエリ増える点は把握しておくこと。

### 1-4. レート制限は Redis 障害時に「許可」へフォールバックする

レート制限は可用性のための仕組みであり、整合性の担保には使っていない。
二重抽選・二重付与の防止は PostgreSQL の冪等性キーが担うため、
Redis が落ちてもデータ破壊は起きない。
ただし**障害中は総当たり攻撃に弱くなる**ため、本番では Redis を冗長化すること。

### 1-5. 汎用景品（`GenericPrize`）は「1 個体 = 1 スロット」原則の例外

ハズレ枠を作らないために、物理在庫を持たない景品を複数スロットへ割り当てられる。
`Inventory` とは別テーブルにすることで、物理在庫側の重複割当禁止（INV-5）は
崩していない。DB の CHECK 制約でどちらか一方のみが設定されることを保証している。

## 2. Phase 1 時点で未実装のもの

Phase 1 は基盤と DB スキーマの確定が範囲。以下は各フェーズで実装する。

| 項目                                          | 担当フェーズ |
| --------------------------------------------- | ------------ |
| 在庫管理画面・オリパ作成・スロット生成        | Phase 4      |
| 1 回抽選 / 10 連抽選の実装                    | Phase 5      |
| ガチャ演出・結果画面・ポイント交換            | Phase 6      |
| 配送先・発送申請・発送管理                    | Phase 7      |
| 監査ログの全面適用・Sentry 接続・E2E シナリオ | Phase 8      |

Phase 2 で認証・RBAC・管理画面基盤を、Phase 3 でポイント台帳と Mock 決済を実装した。
セッション解決は `src/server/session-bootstrap.ts` が読み込み時に登録する
（`instrumentation.ts` だけに任せると、ビルド時のプリレンダリングで未登録になるため）。

seed は Phase 1 の範囲としてユーザー 4 名・架空カード 120 件・汎用景品 1 件を
投入する。オリパ・抽選履歴・ポイント履歴・発送申請のサンプルは、
スロット生成ロジック（Phase 4）に依存するため未実装。

## 3. 運用・環境まわり

### 3-1. `next build` 時は環境変数の相互依存ルールを適用しない

`next build` は `NODE_ENV=production` で動くため、そのままでは
「本番用のシークレットが無いとビルドすらできない」状態になる。
`NEXT_PHASE=phase-production-build` の間は相互依存ルール（本番専用チェック等）を
スキップし、実行時には通常どおり適用する。

その結果、**ビルドが通ったことは本番設定が正しいことを意味しない**。
起動時に初めて検証されるので、デプロイ後のヘルスチェックまで確認すること。

### 3-2. 環境変数の検証失敗はアプリ起動時のクラッシュになる

`serverEnv()` はモジュール読み込み時に評価されるため、設定不備があると
リクエスト処理に入る前に落ちる。この場合のレスポンスは Next.js 既定の 500 になり、
統一エラーフォーマットにはならない（内部情報はクライアントへ出ない）。
意図的な fail-fast だが、ログを見ないと原因が分からない点に注意。

### 3-3. Docker を使わないローカル実行も可能

PostgreSQL / Redis がホストに直接ある場合、`.env` の接続先を変えれば
`docker compose` なしでも動作する。CI ではこちらを使う想定。

### 3-4. テストのクリーンアップは TRUNCATE 必須

追記専用テーブルは DELETE がトリガで拒否されるため、
テストのクリーンアップは TRUNCATE で行う（`src/tests/helpers/setup-db.ts`）。
テスト用 DB の名前に `test` が含まれない場合は、誤って開発 DB を消さないよう
`ALLOW_DESTRUCTIVE_TESTS=1` を要求する。

### 3-5. `prisma migrate reset` は seed も実行する

Prisma 7 では `--skip-seed` が廃止された。
seed を走らせたくない場合は DB を手動で作り直してから
`prisma migrate deploy` を実行する。

## 4. 本番化の前に必ず解消すべきもの

| #   | 項目                                                                                                           |
| --- | -------------------------------------------------------------------------------------------------------------- |
| 1   | 実行時ロール `oripa_app` での接続へ切り替える（追記専用テーブルの UPDATE / DELETE 権限を剥奪した状態で動かす） |
| 2   | DBA ロールの分離と、`draw_order` へアクセスできる人物の限定・監査                                              |
| 3   | 法務確認（賭博罪・景品表示法・資金決済法）と古物商許可の取得                                                   |
| 4   | 正式な決済事業者の審査通過と `PaymentProvider` の差し替え                                                      |
| 5   | Sentry など外形監視の接続                                                                                      |
| 6   | バックアップ・リストア手順の実地検証                                                                           |
| 7   | `SITE_ACCESS_MODE` の扱いと特商法表記・利用規約の整備                                                          |
| 8   | Redis の冗長化                                                                                                 |

詳細は [11-production-checklist.md](./11-production-checklist.md) を参照。
